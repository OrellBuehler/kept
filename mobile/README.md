# Kept for Android and iOS

Native apps for a Kept server you host yourself. On first start the app asks for the address of
your server (`kept.example.org`, or `http://192.168.1.5:3000` inside your network), then for your
Kept username and password. Nothing is sent anywhere else.

- **Android**: Jetpack Compose, `androidApp/`
- **iOS**: SwiftUI, `iosApp/` (project generated by XcodeGen)
- **Shared**: Kotlin Multiplatform, `shared/`: server address, sign-in, the session token, the
  calls of the [app API](../docs/app-api.md) and the reminder planning

The server must be Kept 0.6 or newer (the first version with `/api/app/v1`).

**Get the apps.** Android: the APK attached to the
[releases](https://github.com/OrellBuehler/kept/releases). iPhone: the public beta on
[TestFlight](https://testflight.apple.com/join/qVyFqZ15) (install Apple's TestFlight app first, then open the link on the phone).

## What the apps do

Everything the web does, on the same data: overview, accounts and transactions, bills (add one
from a photo, a scan or a PDF, match payments), budgets, forecast, recurring payments, the year
in review, investments, pillar 3a, taxes, reports, imports and the settings for categories,
preferences, notifications and market data. A few pages open in the browser instead: security
settings (two-step verification, passkeys), API tokens, Paperless and the administrator pages.

**Reminders.** The app can remind you of bills that are due or overdue, budgets that are used up
and accounts without a recent import (Settings → Reminders). There is no push service: the app
asks your server in the background (roughly every six hours, when the system allows it) and
notifies locally, and it schedules the due-date reminders ahead so they arrive even while the
server cannot be reached.

**Sign-in.** Password, plus an authenticator or recovery code when the account has two-step
verification. Or **Sign in with the browser**: the app opens your server's own login page, where
passkeys and password managers work as on the web, and takes over the session when you confirm
there (the server must be Kept 0.7 or newer). The app's own form cannot use passkeys, because a
passkey is bound to your server's address and an app can only be tied to addresses known when it
is built. The session token is kept in the Android Keystore / iOS Keychain; signing
out or changing the password on the web ends it.

## Build

```bash
# Android (JDK 17 and the Android SDK)
cd mobile
./gradlew androidApp:assembleDebug                      # androidApp/build/outputs/apk/debug/
./gradlew shared:allTests androidApp:testDebugUnitTest
./gradlew shared:ktlintCheck androidApp:ktlintCheck androidApp:lintDebug

# iOS (macOS with Xcode 27 and XcodeGen)
./gradlew shared:linkDebugFrameworkIosSimulatorArm64
SDK=$(xcrun --sdk iphonesimulator --show-sdk-version)
mkdir -p shared/build/xcode-frameworks/Debug/iphonesimulator$SDK
cp -R shared/build/bin/iosSimulatorArm64/debugFramework/shared.framework shared/build/xcode-frameworks/Debug/iphonesimulator$SDK/
cd iosApp && xcodegen generate && open Kept.xcodeproj
```

To try the app against a local server, run `bun dev` in the repository root and enter
`http://10.0.2.2:5173` in the Android emulator (`http://localhost:5173` in the iOS simulator).

CI builds and tests both apps on every pull request that touches `mobile/`
(`mobile-android.yml`, `mobile-ios.yml`). The debug APK is attached to the Android run.

## Store screenshots

The **Store Screenshots** workflow (`store-screenshots.yml`, started by hand from the Actions tab)
takes the pictures for both stores and attaches them as the artifacts `android-store-screenshots`
(1080 × 1920, the Play phone size) and `ios-store-screenshots` (1320 × 2868, the 6.9 inch App
Store slot). It also runs on pull requests that change the capture or the example data.

Each job starts a throwaway server (`scripts/screenshots/server.sh`: a fresh SQLite database, one
user, the made-up household of `../scripts/seed-demo`), builds the debug app and starts it once per
screen (`scripts/screenshots/android.sh`, `ios.sh`). A debug build takes the server, the user and
the page to open as intent extras (Android) or launch arguments (iOS), signs in by itself and
opens the page; release builds do not contain that code path. The list of screens is at the end
of `server.sh`.

To run it on your own machine, with an emulator running and the debug app installed:

```bash
mobile/scripts/screenshots/server.sh /tmp/kept-shots
mobile/scripts/screenshots/android.sh /tmp/kept-shots /tmp/kept-shots/out
kill "$(cat /tmp/kept-shots/server.pid)"
```

`bun run store:promo` turns the raw pictures into what the stores show: a headline above a framed
phone for each store size (`play-phone`, `ios-6.9`) and the Play feature graphic. It needs a
Chromium (`CHROME` names the binary) and the two downloaded artifacts:

```bash
gh run download <run id> -D /tmp/kept-shots
bun run store:promo --android /tmp/kept-shots/android-store-screenshots \
  --ios /tmp/kept-shots/ios-store-screenshots --out /tmp/kept-promo
```

The slides and their texts are at the top of `../scripts/store-promo/render.ts`.

## Release

The apps are released together with the server: publishing a GitHub release (tag such as
`v0.6.0`) runs `mobile-release.yml`, and the tag is the version in both stores. Starting the
workflow by hand from the Actions tab (inputs: `version`, and `platforms` = both, android or
ios) only retries a platform of a release that already exists.

- **Versions**: the tag without `v` is the Android `versionName` and the iOS
  `MARKETING_VERSION`. The workflow run number is the iOS build number and is folded into the
  Android `versionCode` (`(major*10000 + minor*100 + patch) * 1000 + run number`), so re-runs
  always increase.
- **Android job**: builds a signed AAB and APK, uploads both as workflow artifacts, attaches them
  to the GitHub release as `kept-<version>.apk` and `.aab`, and uploads the AAB to the Google
  Play internal testing track when `GOOGLE_PLAY_SERVICE_ACCOUNT_JSON` is set.
- **iOS job**: checks the stored provisioning profile, builds the shared release framework,
  archives with App Store Connect API key cloud signing, removes the development certificates
  that cloud signing created, exports with manual signing (Apple Distribution certificate and the
  stored profile), verifies the signature and uploads to TestFlight. The IPA is kept as workflow
  artifact.

A platform whose secrets are missing is skipped when a release is published (the run says which
secrets it misses), so server releases are never blocked by the apps. Started by hand, the
workflow fails instead and names them. No repository variables are used.

| Secret | Job | Content |
|---|---|---|
| `ANDROID_KEYSTORE_BASE64` | Android | The signing keystore, base64 on one line: `base64 -w0 release.jks \| gh secret set ANDROID_KEYSTORE_BASE64` |
| `ANDROID_KEYSTORE_PASSWORD` | Android | Keystore password |
| `ANDROID_KEY_ALIAS` | Android | Key alias in the keystore |
| `ANDROID_KEY_PASSWORD` | Android | Password of that key |
| `GOOGLE_PLAY_SERVICE_ACCOUNT_JSON` | Android, optional | Play Console service account JSON (plain text). Without it the Play upload is skipped. The app must exist in the Play Console first; a brand-new app may refuse the `completed` release status, then do the first upload by hand. |
| `APP_STORE_CONNECT_API_KEY_BASE64` | iOS | The `.p8` App Store Connect API key (role Admin or App Manager): `openssl base64 -A -in AuthKey_XXXXXXXXXX.p8 \| gh secret set APP_STORE_CONNECT_API_KEY_BASE64` |
| `APP_STORE_CONNECT_KEY_ID` | iOS | Key ID of that API key |
| `APP_STORE_CONNECT_ISSUER_ID` | iOS | Issuer ID of the App Store Connect account |
| `APPLE_TEAM_ID` | iOS | Apple developer team ID (injected into `iosApp/ExportOptions.plist` during the job) |
| `IOS_DIST_CERT_P12_BASE64` | iOS | Apple Distribution certificate with private key, exported as `.p12`, base64 on one line |
| `IOS_DIST_CERT_PASSWORD` | iOS | Password of the `.p12` |
| `IOS_PROFILE_APP_BASE64` | iOS | App Store provisioning profile for `ch.orellbuehler.kept`, base64 on one line: `openssl base64 -A -in Kept_App_Store.mobileprovision \| gh secret set IOS_PROFILE_APP_BASE64` |

One-time Android setup: create a keystore
(`keytool -genkeypair -v -keystore release.jks -keyalg RSA -keysize 4096 -validity 10000 -alias kept`),
keep it and its passwords somewhere safe (losing it means the app can never be updated), and set
the four secrets.

One-time iOS setup: register the App ID `ch.orellbuehler.kept` (no capabilities needed), create
the app in App Store Connect, and create the App Store provisioning profile with the exact name
`Kept App Store` (the name `iosApp/ExportOptions.plist` refers to). If the app gains capabilities
later, regenerate the profile and update the secret.

The app allows plain http (`NSAllowsArbitraryLoads`, `usesCleartextTraffic`) because a
self-hosted server is often reached inside the home network; App Review asks for that reason.
