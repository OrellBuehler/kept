# Mobile (Kotlin Multiplatform)

Native apps for a self-hosted Kept server: Android (Jetpack Compose) and iOS (SwiftUI). The user
enters the address of their own server; nothing is hard-wired. `README.md` has build steps and
the release process.

## Commands

```bash
source ~/.sdkman/bin/sdkman-init.sh && export ANDROID_HOME=~/android-sdk && cd mobile

./gradlew androidApp:assembleDebug
./gradlew shared:allTests androidApp:testDebugUnitTest      # on Linux the iOS test targets are skipped
./gradlew shared:ktlintCheck androidApp:ktlintCheck         # fix with shared:ktlintFormat androidApp:ktlintFormat
./gradlew androidApp:lintDebug
```

CI runs the same (`mobile-android.yml`). Kotlin style comes from `.editorconfig` (ktlint official,
4 spaces, 140 columns).

## How the apps talk to the server

Everything goes through `/api/app/v1` (`docs/app-api.md`): sign-in, `session`, `reminders`, and
the bridge, which runs the `load` and the form actions of the web pages and answers JSON.

- **A page's data is the web page's `load` result.** `GET pages/bills/<id>` is what
  `src/routes/(app)/bills/[id]/+page.server.ts` returns. Read that file (and the types it uses)
  to know what a field means; read the matching fixture in
  `../src/lib/testing/fixtures/app-contract/` to see the exact JSON.
- **An action is the web page's form action.** `POST pages/bills/<id>?_action=allocate` with the
  form's fields as a JSON object of strings. The field names, formats and error keys are the ones
  of the Zod schema the action parses (`src/lib/server/**/schemas.ts`): send what the HTML form
  would send. Amounts are typed text ("1'234.50"), dates `YYYY-MM-DD`, a checkbox is `"on"` or
  absent, an empty optional field is `""` or absent as the schema expects.
- **The page fixtures are the contract.** The server writes `../src/lib/testing/fixtures/app-contract/*.json` from a synthetic
  dataset and fails its tests when a page drops or retypes a field. Every model a screen decodes
  gets a test that decodes the matching fixture (Android: `androidUnitTest/.../data/*ContractTest.kt`
  with `Contract.page<T>("bills")`; iOS: `KeptTests/` with `ContractTests.decode(T.self, "bills")`).
  A field that is `null` in one fixture may hold a value in another capture of the same page.
- Models declare only the fields the screen uses. Unknown fields are ignored on both platforms.
  On iOS a field that can be `null` or missing must be an `Optional` (Swift's synthesized
  `Decodable` does not fall back to a default value); on Android give every field a default.
- Money is integer minor units (`Long` / `Int64`) next to an ISO 4217 code. Never floats. Format
  with `Formats` (Android `LocalFormats.current`, iOS `@Environment(\.formats)`) or the
  `AmountText` component, which also honours the "blur amounts" preference.
- Never log amounts, descriptions, counterparties, IBANs or the session token.

## Modules

- **`shared/`**: `KeptSdk` is the single entry point: server address, sign-in and second factor,
  the session token, the calls of the app API (`page`, `action`, `download`, `endpoint`) and the
  reminder planning. It returns page data as JSON text; it has no page models. Keep what the UIs
  do not need `internal`. Kotlin is bumped only together with SKIE (Dependabot ignores Kotlin).
- **`androidApp/`**: Compose and Material 3. `data/` holds the page models (`@Serializable`) and
  `KeptSdk.load<T>()`, `ui/<feature>/` one package per feature, `ui/components/` the shared
  building blocks, `ui/common/` `PageViewModel`, `Formats` and the composition locals.
- **`iosApp/`**: SwiftUI, project generated by XcodeGen from `iosApp/project.yml` (`*.xcodeproj`
  and `Info.plist` are generated and gitignored; add Info.plist keys in `project.yml`).
  **Only `iosApp/Kept/SDK/` imports `shared`**: `SDKClient` maps to the plain `Sendable` Swift
  values in `SDK/Models.swift`, and page data is decoded into `Decodable` structs next to each
  feature (`Features/<Feature>/<Feature>Models.swift`).

## Screen pattern

Android: a `PageViewModel<T>` subclass per screen (fetch with `sdk.load<T>(path, query)`, one
method per action calling `submit(path, action, FormBody()…)`), rendered inside `PageScaffold`,
which does the title bar, pull to refresh, loading and error states and shows the view model's
messages. Forms are `FormSheet` + the fields in `ui/components/Forms.kt`; field errors come from
`vm.formErrors`. Navigate with the `Navigator` the screen is given (`Routes` are the web paths
without the leading slash, so `nav.openWebPath(redirect)` follows what the server answers).
`ui/dashboard/DashboardScreen.kt` and `ui/settings/SettingsScreen.kt` are the reference.

iOS: `@State private var store = PageStore<T>(path:query:)` rendered inside `PageView`, which
does the same. Actions are `await store.submit("action", form: FormFields([...]))`; forms are a
`.sheet` with `FormSheet`. Navigate with `NavigationLink(value: Route.…)` or the `Router` from
the environment. `Features/Dashboard/` and `Features/Settings/SettingsView.swift` are the reference.

Rules for both:

- Every feature ships on Android and iOS. Implement both, or say in the commit message which one
  is deferred.
- The app is English only, like the web. Android: no hardcoded UI text (lint `HardcodedText` is an
  error); strings live in `res/values/strings_<feature>.xml`. iOS: plain literals in the views.
- What the app has no screen for opens in the browser (`nav.openInBrowser`, `router.openInBrowser`):
  security settings, API tokens, Paperless, user administration, backups.
- A choice with long labels or more than three options is a dropdown (`ChoiceField`, `Picker`),
  not segmented buttons. In a row of label and value the label takes the free width.
- Dates are shown with `Formats` (the user's locale from Kept's preferences), never as raw ISO text.
- Destructive actions ask first (`ConfirmDialog`, `.confirmationDialog`).

## Reminders

No push service: the device asks `GET /reminders` (when the app opens, and periodically in the
background: WorkManager on Android, `BGAppRefreshTask` on iOS), shows events it has not shown
before, and schedules local notifications for the due dates of open bills. `shared` decides what
to show (`Reminders.plan`, tested in `commonTest`); the platform code only posts and schedules
(`reminders/ReminderScheduler.kt`, `Reminders/ReminderScheduler.swift`). The settings live on the
device.

## iOS is compile-gated by CI

There is no Swift compile on Linux. Do not try to compile Swift locally. Push, then read the iOS
checks: `ios-build` first (shared framework plus simulator app build), then `ios-tests`
(Kotlin/Native tests of `shared`, then the app's unit tests on a simulator); `ios-gate` is the
always-reporting required check.

Swift 6 language mode, deployment target iOS 18. Check new Swift against these before pushing:

- Views and stores are `@MainActor`; models are `Sendable` structs. Kotlin types never leave
  `SDKClient` (the one place with `@preconcurrency import shared` and `@unchecked Sendable`).
- Pure helpers on a `@MainActor` type (a `static` function or `static let` that only uses its
  arguments) are `nonisolated`, otherwise they cannot be called from tests or background code.
- Delegate callbacks with non-Sendable arguments are `nonisolated`; copy plain values out and hop
  to the main actor.
- A `[weak self]` belongs on the innermost closure that uses `self`; a `@Sendable` closure must
  not capture a weak `self` declared by an outer closure.
- Kotlin `Int` is `Int32` and `Long` is `Int64` in Swift, a nullable `Long` is `KotlinLong?`;
  default arguments do not exist. Convert at the boundary in `SDKClient`.
- Split expressions the compiler cannot type-check in time (long `+` chains of strings and
  optionals, big literals, deeply nested view builders): give sub-views their own function or
  struct. That failure shows up only in CI.
- Grep before adding a type: every Swift file is in one module, so two features must not both
  declare `struct Category` or `struct Account`. Nest a page's types inside its page struct or
  prefix them with the feature (`BillsPage.Row`, `AccountDetail.Transaction`).

## CI and release

`mobile-android.yml` and `mobile-ios.yml` gate every PR that touches `mobile/`;
`mobile-release.yml` ships signed builds when a GitHub release is published (secrets table in
`README.md`). Actions are pinned to commit SHAs with a version comment: keep that when bumping.
Signing material (`*.jks`, `*.p12`, `*.mobileprovision`) is gitignored and must never be
committed. `iosApp/ExportOptions.plist` has no team id (the workflow injects it) and its profile
name `Kept App Store` must match the provisioning profile.

The API is additive-only, and the server is released before the app builds that need a new field
or page: an older app must keep working against a newer server.
